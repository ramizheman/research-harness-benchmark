# Benchmark design: does research memory make an AI research agent better?

Status: design only. Nothing in this document has been run.

## 1. Questions the benchmark answers

The benchmark is about the research harness, not about basketball.

- **Q1, memory versus none.** Does access to the accumulated research history, failures included, improve an AI research agent's performance on basketball research tasks? This compares condition B with condition A.
- **Q2, structure versus documents.** Given the same information, does structured memory improve performance over searchable documents? This compares condition C with condition B.
- **Q3, negative transfer.** Does memory make the agent worse on tasks where the history is irrelevant, for example by making it over-cautious?

**Prior work.** No claim is made that this benchmark is novel. Before any write-up, the following should be reviewed and the overlap recorded:
- benchmarks of AI agents on data-driven discovery and scientific analysis (for example DiscoveryBench, ScienceAgentBench and MLAgentBench);
- end-to-end automated research systems (for example "The AI Scientist");
- crowdsourced many-analyst studies of one dataset, which include a soccer refereeing dataset (Silberzahn et al., 2018).

## 2. Conditions

| | A: no history | B: document memory | C: structured memory |
|---|---|---|---|
| Research history | none | `memory\documents\*.md` (384 files) with a full-text search tool | `memory\graph_nodes.jsonl` and `graph_edges.jsonl` with a graph query tool and text search over node properties |
| Information content | none | identical to C (checked by `scripts\06_equivalence_check.py`, 0 mismatches) | identical to B |

**Held identical across all three conditions:**
- **Model:** the same model version, temperature and sampling settings.
- **Instructions:** the same system prompt, apart from one sentence naming the memory tool in B and C.
- **Task:** the same task statement and objective.
- **Data:** the same frozen snapshot of the basketball data (Neo4j graph export and play-by-play files), with the same read access.
- **Analysis tools:** the same sandbox (Python, SQL or Cypher over the data), the same libraries, no web access.
- **Budget:** the same token, tool-call and wall-clock limits. Memory queries count against the same budget, so B and C pay for retrieval.
- **Output format:** the same required format and the same evaluation.

**Memory tools.** Both tools return plain text with the same truncation limit per call. The B tool searches documents by keyword and returns ranked file excerpts. The C tool accepts a node id, a node type and filter, or a one- or two-hop traversal, and returns the matching nodes and edges with their provenance.

**Possible extension, outside the primary comparison.** A fourth arm, C+B (both tools), would test whether structure adds value on top of documents rather than replacing them.

## 3. Memory construction per task

### 3.1 Chronological cutoff

For a task tied to a date, both memories contain only records dated before that date.

**Prerequisite:** dates must first be checked by hand. 205 of 384 records are dated by file modification time (`data_quality_and_classification_audit.md`, section 8).

### 3.2 Answer removal

For a replay task based on study family F, both memories exclude:
- every member of F;
- every record that names a member of F in its `related` field;
- every record dated after the task date.

The exclusion lists are generated by script and stored with the task.

### 3.3 Memory variants

The cutoff and exclusions change memory per task. Both B and C are regenerated from the same filtered record list by `scripts\01_build_inventory_and_memory.py`, run with a record filter (to be added). The equivalence check runs on every variant.

## 4. Data splits and held-out material

| split | content | use |
|---|---|---|
| Historical data | seasons used in the history (records mention 2020-21 to 2025-26) | replay tasks |
| 2025-26 | used by many strategy-app and suppression records; excluded from the lineup-adaptation analyses at the researcher's request | not held out. Replay tasks derived from the lineup-adaptation project must not use it. |
| 2026-27 through a freeze date D1 | no record uses 2026-27 data | prospective challenges: development data |
| 2026-27 from D1 to D2 (for example the second half of the season and the playoffs) | sealed until all agent claims are registered | prospective challenges: validation data |

**Contamination.** The published papers (Structural Influence and Detecting Defensive Suppression) may be in a model's pretraining data. Required controls:
1. Prefer models whose stated training cutoff predates March 2026.
2. Before the runs, probe each model in condition A with 20 questions about specific recorded results, such as the published suppression excess or the Paper 1 coverage test estimate. Report its accuracy.
3. Exclude, or analyse separately, any task the model can answer from memory in condition A.
4. Disable web access.

## 5. Task types

### 5.1 Retrospective replay tasks (criteria 1 to 4)

Each task presents a historical research question as it stood on its original date, with the memory cut off as in section 3. Contents:
- the hypothesis text;
- the data available at that date;
- the objective;
- a budget.

The agent must produce four things, in order:
1. A testability judgment with a probability: can this question be answered with the available data at a useful power? If not, why not?
2. A check against prior work: does the history already answer this, and with what result and scope?
3. A list of methodological and statistical risks specific to the design.
4. Either a preregistration-quality design (estimand, unit, sample, power or MDE, controls, falsification tests, decision rule), or a recommendation not to proceed, with reasons.

Execution is optional and off by default for replay tasks. Scoring is against adjudicated history, not against new results.

**Task pool.** Only study families whose labels pass adjudication are eligible (section 9, prerequisites 1 to 3). Tasks are sampled by stratum so that no fixed strategy, such as "always say it will fail", can score well:

| stratum (adjudicated status) | families available now | tasks |
|---|---|---|
| supported | 55 | 16 |
| adequately rejected | 62 (upper bound) | 16 |
| untestable with available data | 58 | 16 |
| artifact | 50 | 16 |
| genuinely uncertain | 14 | 14 (all) |

Within each stratum, no more than 4 tasks come from one question cluster (`failure_analysis.md`, section 2). This keeps the adaptation cluster from dominating.

**Redundancy subset.** A replay task counts as a redundancy task when, after the cutoff, its memory still holds an earlier family that asked the same question (judged by adjudicators). The prior answer is then legitimately available in B and C and missing in A.

### 5.2 Prospective held-out challenges (criteria 4 to 8)

These are open research objectives on 2026-27 data through D1. They are written by an independent basketball analyst who has not seen the agents' outputs and who did not take part in the history.

**Requirements for each challenge:**
- an objective statement at the level of "find X about Y", not a hypothesis;
- the data and fields available;
- a budget;
- what counts as a deliverable claim: a single registered finding with an estimand, a direction and a prespecified validation test.

**Challenge mix** (the challenge writer assigns each challenge before any run):
- **History-relevant challenges:** the most natural first approach meets a constraint recorded in the history, such as unit exposure, measure reliability or label leakage.
- **History-irrelevant challenges:** the history has nothing that bears on the objective. These measure negative transfer (Q3).

The challenges are not repeats of historical questions. The writer checks each one against `experiment_inventory.csv`, and an adjudicator confirms.

**Claim registration and validation:**
1. Each run ends by registering at most 3 claims, each with its validation test.
2. Claims are frozen (hashed and timestamped) before the validation data D1 to D2 is released.
3. Validation is run by a human analyst blind to condition, using the registered test.

**Note on this document.** No challenge objectives are written here. Writing them is the independent analyst's job, and the task constraints rule out generating new basketball hypotheses.

## 6. Evaluation criteria and measures

| # | criterion | task type | measure | scored by |
|---|---|---|---|---|
| 1 | Early identification of unanswerable questions | replay | Brier score and AUC of the testability probability against the adjudicated testable or untestable status; budget (tokens and tool calls) spent before the first untestability flag; false-flag rate on testable tasks | script, against adjudicated labels |
| 2 | Avoiding redundant experiments | replay (redundancy subset), prospective | Share of proposals classed as redundant (same estimand, data and design as a prior family with no material change) vs incremental vs materially new. Condition A is scored against the history too. | two blinded reviewers |
| 3 | Detecting methodological and statistical risks | replay | Recall and precision against a per-task risk checklist written by adjudicators before any run. The checklist is drawn from the artifact and limitation mechanisms in `failure_analysis.md`, sections 3 to 5: selection on early performance, labels derived from outcomes, in-sample calibration, ranking small cells, placebos that share noise, mechanical floors, power and MDE, measure reliability, team-quality confounding. | two blinded reviewers |
| 4 | Design quality | replay, prospective | Preregistration rubric, 0 to 2 on each of 8 items: estimand, unit and sample, power or MDE, controls, falsification and placebo tests, multiplicity, decision rule, data-version awareness | two blinded reviewers |
| 5 | Novelty | prospective | Each claim checked against (a) the full history and (b) published sports-analytics research, using a recorded search protocol (Google Scholar, arXiv stat.AP, Journal of Quantitative Analysis in Sports, MIT Sloan Sports Analytics Conference papers; search strings and hits logged). Classed as known, partially known or not found. No claim counts as novel without a search record. | one reviewer, checked by a second |
| 6 | Survival under validation | prospective | Share of registered claims that pass their registered test on D1 to D2 data, plus an independent reanalysis by a human analyst | blinded analyst |
| 7 | Practical usefulness | prospective | 1 to 5 rating by a panel of at least 2 basketball practitioners: decision relevance, effect size in game terms, actionability | blinded panel |
| 8 | Validated discoveries per unit of effort | prospective | Number of claims that survive (criterion 6), are not known (criterion 5) and are rated at least 3 (criterion 7), divided by tokens, wall-clock and reviewer hours. Reported per 1M tokens and per run. | derived |

**Primary outcomes** (prespecified, Holm-corrected across the two):
- **P1, replay:** a balanced wasted-effort score. On replay tasks, the mean of (a) the share of untestable, artifact and redundancy tasks correctly flagged before design, and (b) the share of supported, rejected and uncertain tasks not falsely flagged.
- **P2, prospective:** validated discoveries per run (criterion 8).

Everything else is secondary.

**Ground-truth caution.** Labels for criteria 1 to 3 come from the adjudicated history, which is itself uncertain. Every replay result is reported both with adjudicated labels and restricted to tasks where two independent coders agreed.

## 7. Blinding

- **Redacting outputs:** before any review, each output passes through a script that turns memory citations (record ids, file names, "the history shows") into neutral tokens such as "[prior result]". The script also removes tool names. A second person spot-checks 10% of outputs.
- **Reviewer independence:** reviewers are not the researcher who produced the history, and they do not know which condition produced which output.
- **Checking the blind:** after scoring, reviewers guess each output's condition. Guess accuracy is reported. If it is well above chance (for example, more than 50% correct among 3 conditions), the review-based criteria are reported as unblinded.

## 8. Design, sample size and analysis

**Runs:**
- **Pilot and main study:** one model family (stage 1 and stage 2).
- **Stage 4:** at least two more model families, with the identical protocol.
- **Seeds:** 3 independent seeds per task, condition and model.

**Replay arm sample size.** 78 tasks (section 5.1), 3 conditions, 3 seeds: 702 runs per model.
- **Power:** for a paired task-level contrast at two-sided α = 0.025 (Holm with two primaries), 78 tasks give about 80% power for a standardized task-level difference of 0.35, and about 98% for 0.5.
- **Confirming the assumption:** the standardization assumes task-level SD estimated in the pilot. The pilot (10 tasks) is used to confirm it, with simulation-based power for the mixed model.

**Prospective arm sample size.** 12 challenges (6 history-relevant, 6 history-irrelevant), 3 conditions, 3 seeds: 108 runs per model, each with up to 3 claims.
- **Estimation, not testing:** validated discoveries are expected to be rare, so P2 is reported as a rate ratio with a 95% interval, and a null result is interpreted only in the light of that interval width.

**Models:**
- **Binary or proportion outcomes:** mixed-effects logistic or linear models, with outcome ~ condition + (1 | task) + (1 | task:seed), plus model family as a fixed effect in stage 4.
- **Contrasts:** B minus A and C minus B.
- **Q2 equivalence:** for C against B, a TOST equivalence test with a margin of ±0.10 on P1. Absent a meaningful gain, documents are retained as the cheaper option.
- **Q3:** a one-sided test that B and C are not worse than A by more than 0.10 on history-irrelevant challenges.
- **Cost:** all criteria also reported per 1M tokens.

**Pre-registered decision rule:**
1. **Memory helps** if B minus A on P1 is positive with a Holm-adjusted p below 0.05, the lower 95% bound exceeds 0.05, and negative transfer is ruled out at the 0.10 margin.
2. **Structure helps** if C minus B on P1 or P2 meets the same standard.
3. **No case for the graph** if C and B are equivalent within the margin. Building and maintaining a graph is then not justified by this evidence.
4. **Otherwise inconclusive.** The report then gives the achieved intervals and the sample size a decisive test would need.

## 9. Prerequisites before any run

Taken from `data_quality_and_classification_audit.md`:
1. **Adjudicate the families.** Resolve the 20 study families with conflicting verdicts. Assign a final, per-test verdict and mechanism, with an explicit hypothesis statement for each replay-eligible family.
2. **Double-code a sample.** Code at least 60 families twice, and require kappa of at least 0.6 on verdict and mechanism.
3. **Re-rate in-advance knowability blind.** Re-rate `knowable_in_advance` by reviewers who see only pre-outcome information.
4. **Write the answer key.** Human curators write `what_was_learned`, `ruled_out_directions` and `viable_directions` for replay-eligible families. These form the answer key for criteria 1 and 2.
5. **Fix dates.** Check dates for every record used in a cutoff.
6. **Close coverage gaps.** Extract the coverage gaps likely to contain scoreable predictions (`PREGAME_*`, the `reports` folder, the 2026 backtest logs) or document their exclusion.
7. **Add the record filter** to the build script and re-run the equivalence check for each memory variant.
8. **Write the prospective challenges** (independent analyst) and fix D1 and D2.
9. **Run the contamination probes.**

## 10. Stages

| stage | content | exit condition |
|---|---|---|
| 0 | Prerequisites 1 to 9 | all done; adjudicated task pool of at least 78 |
| 1, pilot | 10 replay tasks and 2 challenges, 1 model, 3 conditions, 1 seed | budget adequate (fewer than 10% of runs hit a limit), redaction works, variance estimate for power |
| 2, main replay | 78 tasks, 3 seeds, 1 model | analysis per section 8 |
| 3, prospective | 12 challenges, validation after D2 | analysis per section 8 |
| 4, model families | repeat stages 2 and 3 on at least 2 more model families | condition-by-model interaction reported |

## 11. Threats to validity

| threat | mitigation |
|---|---|
| The answer leaks through memory in replay | answer removal and cutoff (section 3), exclusion lists stored per task, audit of 10% of runs for citations of excluded records |
| Pretraining contamination | contamination probes; models with cutoffs before the history; separate analysis of probed tasks |
| Pessimism bias (memory teaches "everything fails") | stratified task pool with supported and uncertain strata; balanced P1; negative-transfer test on irrelevant challenges |
| Unreliable ground truth | adjudication, double coding, reporting on the agreed-label subset |
| Reviewer unblinding | redaction, blind check, reporting unblinded criteria separately |
| B and C differ in reading cost as well as structure | identical information checked by script; the budget counts retrieval; tokens spent on memory reported per condition |
| Goodhart on the risk checklist | the checklist is written per task by adjudicators and not shown to agents; precision is scored as well as recall |
| A small number of prospective challenges | report as estimation with intervals; do not over-interpret P2 |
| The history comes from one researcher's pipeline | findings about memory value may not transfer to other research groups or sports; state this as a limit of scope |
